## Общая схема

```text
                    ┌──────────────────────────────────────────┐
   Браузер ────────▶│  Nginx  :9162                            │
                    │    /       → /var/www/ravix  (Vite dist) │
                    │    /api/   → 127.0.0.1:8080              │
                    └───────────────────┬──────────────────────┘
                                        │
                             ┌──────────▼───────────┐
                             │  Бэкенд Quarkus      │
                             │  sh.ravix.*          │
                             └──┬────────────────┬──┘
                                │                │
                  ┌─────────────▼──┐    ┌────────▼──────────────────────┐
                  │  PostgreSQL    │    │  Linux-хост                   │
                  │  схема: ravix  │    │  systemd · apt · postmap      │
                  │  владеет Flyway│    │  /etc/postfix · /etc/dovecot  │
                  └────────────────┘    │  DNS · certbot · логи         │
                                        └───────────────────────────────┘
```

Ravix — **не почтовый сервер**. Это control plane, который владеет конфигурацией
и наблюдаемостью почтового сервера, работающего на том же хосте.

## Структура пакетов бэкенда

Весь код бэкенда лежит под `sh.ravix`:

| Пакет | Ответственность |
| --- | --- |
| `auth` | Аутентификация, сессии, TOTP-2FA, BCrypt, проверка ролей, аудит-фильтр, контекст арендатора. |
| `entity` | Panache-сущности — персистентная модель. |
| `dto` | Формы ответов, не являющиеся сущностями. |
| `rest` | JAX-RS-ресурсы; по одному на доменное понятие, все под `/api`. |
| `platform` | Всё, что общается с внешним миром: провижининг хоста, DNS, ключи DKIM, сертификаты, очередь, рассылки, сканеры DMARC/FBL/RBL, Cloudflare. |
| `util` | Мелкие общие хелперы (генерация ID). |

Основная сложность сосредоточена в `platform`. `ProvisioningService` — самый
большой класс в кодовой базе не случайно: он рендерит всю конфигурацию почтового
стека из состояния в базе.

## Жизненный цикл запроса

1. Nginx терминирует TLS и проксирует `/api/` на `127.0.0.1:8080`.
2. `AuthFilter` определяет вызывающего — сначала по cookie `ravix_session`,
   затем по заголовку `Authorization: Bearer` — и резолвит его в `AdminUser`
   через `AuthService`, отклоняя неаутентифицированные запросы ко
   всему, кроме небольшого списка публичных путей (`/api/auth/login`,
   `/api/auth/status`, пиксели трекинга, `.well-known`).
3. `OrgFilterInterceptor` применяет скоупинг по арендатору к ресурсам с
   аннотацией `@OrgFiltered`, опираясь на организацию резолвнутого пользователя
   — см. [Мультитенантность](multi-tenant.md).
4. `AuditFilter` пишет изменяющие запросы в `audit_log`.
5. Ресурс выполняется — обычно читает Panache-сущности, иногда вызывает сервис
   из `platform`, который дёргает хост.

## Сессии и API-ключи

К одному и тому же API приходят два типа учётных данных:

- **Сессионные токены** — выдаются `/api/auth/login`, хранятся в таблице
  `auth_session` и возвращаются браузеру в виде `HttpOnly`-cookie с
  `SameSite=Strict`. Токен есть и в теле ответа — для не-браузерных клиентов.
  Опционально защищены TOTP-2FA и ограничены `LoginRateLimiter`.
- **API-ключи** — `rvx_live_<random>`, генерируются `ApiKeyService`. Хранятся
  только BCrypt-хеш и последние четыре символа, поэтому ключ показывается ровно
  один раз при создании. Используются для
  [транзакционной отправки](api.md).

## Кто владеет состоянием

Это правило объясняет бо́льшую часть дизайна:

> **PostgreSQL — источник истины. Конфиги почтового стека — производный
> артефакт.**

Домены, ящики, алиасы, фильтры и подписи живут в базе. По нажатию **Применить**
`ProvisioningService` рендерит их в карты Postfix, файл пользователей Dovecot,
таблицы ключей OpenDKIM и оверрайды Rspamd, выполняет `postmap` и перезагружает
сервисы. Править `/etc/postfix/ravix/*` руками бессмысленно — следующее
применение перезапишет.

Ravix пишет в выделенные подкаталоги (`/etc/postfix/ravix/`,
`/etc/rspamd/local.d/`, `/etc/dovecot/ravix-users`), а не заменяет основной
конфиг дистрибутива — так ваши ручные настройки вне этих путей выживают.

## Почему бэкенд работает от root

Ravix ставит пакеты через `apt`, пишет в `/etc/postfix` и `/etc/dovecot`,
запускает `postmap`, управляет юнитами `systemd` и читает root-only логи.
Поэтому systemd-юнит в 0.1 использует `User=root`.

Это крупнейшая известная слабость текущего дизайна: любое удалённое выполнение
кода в панели — это сразу root на почтовом хосте. Задуманное решение — узкий
привилегированный хелпер с профилем `sudoers`, чтобы сам бэкенд мог опуститься
до пользователя `ravix`. Пока этого нет, считайте доступ к панели равным
root-доступу и соответственно ограничивайте порт панели — см.
[Безопасность](security.md).

## Фоновые задачи

| Сервис | Что делает |
| --- | --- |
| `DomainChecker` | Живые проверки MX / SPF / DKIM / DMARC / PTR по доменам. |
| `DmarcScanner` | Обрабатывает агрегированные отчёты из входящего каталога DMARC. |
| `FblScanner` | Обрабатывает ARF-жалобы и ведёт список подавления. |
| `RblScanner` | Проверяет отправляющие IP по DNSBL. |
| `ReputationService` | Скользящая оценка репутации за 30 дней. |
| `CampaignSender` | Отправка рассылок с троттлингом и лимитами прогрева. |
| `QueueService` | Чтение и управление очередью Postfix. |
| `TaskService` | Отслеживание долгих фоновых задач, показываемых в UI. |

DNS-запросы идут через встроенный провайдер JDK
(`com.sun.jndi.dns.DnsContextFactory`) — именно поэтому выставлен
`quarkus.naming.enable-jndi=true`. Quarkus отключает JNDI по умолчанию, и без
этого флага все DNS-проверки молча возвращали бы пустоту.

## Фронтенд

Обычное Vite-SPA. Что стоит знать:

- **i18n.** Русский — язык по умолчанию, английский полный; выбор хранится в
  `localStorage`. `src/i18n/ru.ts` и `src/i18n/en.ts` должны быть синхронны —
  тест падает при расхождении ключей.
- **Аутентификация.** Сессия — это `HttpOnly`-cookie, которую браузер
  подставляет сам, поэтому ни один скрипт — ни наш, ни внедрённый — её не
  прочитает. В `localStorage` остаётся только булев признак «вошли», нужный для
  выбора начального маршрута; источник истины — сервер, а устаревший признак
  просто приведёт к 401 и редиректу на `/login`.
- **Вебмейл.** `WebmailPage.tsx` рендерит тела писем через DOMPurify. Почта
  сейчас лежит в PostgreSQL, а не читается по IMAP.

## Тесты

| Набор | Команда | Что покрывает |
| --- | --- | --- |
| Юниты бэкенда | `cd backend && mvn test` | Разбор MIME, сборка писем, сертификаты, рендер провижининга, генерация ID. |
| Интеграционные | `cd backend && mvn verify` | Флоу аутентификации, авторизацию, фильтрацию по арендаторам — на реальном PostgreSQL через Testcontainers (нужен Docker). |

CI прогоняет все три на каждый push и pull request.
