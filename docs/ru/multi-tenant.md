# Мультитенантность

[← К оглавлению](README.md) · [English](../en/multi-tenant.md) · [中文](../zh/multi-tenant.md)

---

> **Статус: реализовано, но не обкатано в бою.** Модель бэкенда, Hibernate-фильтр
> и тест изоляции на уровне персистентности готовы. Фронтенд покрыт частично, и
> модель ещё не проверялась реальным мультиклиентским развёртыванием. Считайте
> изоляцию арендаторов границей безопасности, которую стоит проверить самому,
> прежде чем продавать на ней хостинг.

## Модель

Одна установка Ravix, **один почтовый стек**, много независимых организаций.

Это важно: почтовый слой на уровне ОС общий по замыслу. Postfix маршрутизирует
только по домену получателя и не имеет понятия о владельце домена — поэтому
существует один набор карт `virtual_domains`, один файл пользователей Dovecot и
одна таблица ключей OpenDKIM на всех арендаторов. Домены глобально уникальны в
пределах установки.

**Изоляция логическая и обеспечивается на уровне приложения**, а не отдельными
экземплярами Postfix или Dovecot. Организация видит только свои строки; сам
почтовый стек остаётся под контролем оператора.

## Сущности

| Сущность | Назначение |
| --- | --- |
| `Organization` | Арендатор: имя, slug, статус, квоты по доменам, ящикам и объёму. |
| `OrgMembership` | Связывает `AdminUser` с `Organization` и ролью. |
| `AdminUser.superadmin` | Флаг оператора платформы — обходит весь скоупинг. |

Пользователь может состоять в нескольких организациях (сотрудники оператора);
типичный случай — один пользователь в одной организации.

### Скоупятся по арендатору

Эти несут `org_id` и фильтруются в каждом запросе:

`domain`, `mailbox`, `alias`, `campaign`, `campaign_recipient`, `segment`,
`contact`, `email_template`, `mail_filter`, `mail_signature`, `inbox_seed`,
`inbox_test`, `api_key`

### Глобальные (операторские)

Инфраструктура и наблюдаемость принадлежат оператору, а не арендатору:

`app_setting`, `service_status`, `package_status`, `queue_item`, `log_line`,
`install_log`, `certificate`, `dns_record`, `rbl_check`, `dmarc_report`,
`fbl_complaint`, `audit_log`, `background_task`, `warmup_config`, `backup`

Некоторые из них можно было бы *показывать* по арендаторам — свои элементы
очереди или DMARC-отчёты — но принадлежат они не одному из них.

## Роли

Роли назначаются пользователю и проверяются в `AuthFilter`:

| Роль | Что может |
| --- | --- |
| `owner` | Всё, включая управление участниками команды. |
| `admin` | Полный контроль над почтовой платформой; **не может** добавлять, удалять и менять роли других администраторов. |
| `viewer` | Только чтение. Может менять лишь свой пароль и 2FA. |

`Roles.normalize()` сводит легаси- и произвольные значения (`Administrator`,
`read-only`, разный регистр) к этому набору; всё нераспознанное становится
`admin`.

Ортогонально всем трём — `superadmin`: это *платформенный* флаг, а не роль, и он
полностью обходит скоупинг по организациям.

## Как обеспечивается изоляция

Четыре механизма, намеренно наслоённых, чтобы одна ошибка не приводила к утечке:

1. **`TenantContext`** — request-scoped бин, определяющий эффективную
   организацию вызывающего; заполняется в `AuthFilter.resolveTenant()`.
2. **Hibernate `@Filter("orgFilter")`** на каждой скоупируемой сущности,
   включается на запрос и добавляет `org_id = :orgId` к запросам.
3. **`OrgStamp` — слушатель `@PrePersist`** — проставляет `org_id` из контекста
   при создании, так что ни один путь записи не может его забыть.
4. **HQL для выборок по id.** REST-ресурсы используют
   `find("id", …).firstResult()`, а не `findById()`, потому что загрузка по
   первичному ключу полностью обходит фильтры Hibernate. Это неочевидный момент
   — именно он заставляет `GET /api/domains/<чужой-id>` вернуть 404, а не строку.

Супер-админ по умолчанию работает без скоупа и может действовать внутри одного
арендатора, передав заголовок `X-Ravix-Org` или query-параметр `org`.

Межорганизационные чтения и записи возвращают **404, а не 403** — 403 подтвердил
бы существование строки.

## Как проверить изоляцию самому

`TenantFilterTest` покрывает слой персистентности на реальном PostgreSQL: три
домена в двух организациях, проверка, что каждая видит только свои и что без
фильтра все строки на месте.

Это доказывает, что фильтр работает на сессии. Это **не** доказывает, что все
~39 REST-ресурсов задействуют его корректно. Прежде чем доверять этому в
продакшене, проверьте end-to-end на работающем сервере:

1. Создайте организацию B; положите один домен в Default и один в B.
2. Добавьте пользователя без `superadmin` только в B.
3. Войдите под ним — `GET /api/domains` должен вернуть **только** домен B.
4. `GET /api/domains/<id-домена-из-Default>` должен вернуть **404**.
5. Супер-админ без `X-Ravix-Org` видит оба; с `X-Ravix-Org: <B>` — только B.

Если шаги 3 или 4 текут, фильтр не включается на сессии запроса — лечится
включением внутри транзакции через CDI-интерцептор на ресурсах арендаторов, а не
в JAX-RS-фильтре. Если столкнулись —
[сообщите](https://github.com/tnAnGel/Ravix/issues).

## Квоты

`Organization` несёт `quota_domains`, `quota_mailboxes` и `quota_storage_mb`.
`0` означает «без ограничений». Принуждение реализовано не полностью — в 0.1
считайте поля квот рекомендательными, а не жёстким лимитом.

## Миграция и обновление

`V13__multi_tenant.sql` обратно совместима. Обновление однопользовательской
установки создаёт одну организацию `Default`, переносит в неё все скоупируемые
строки и делает существующего администратора её владельцем с флагом
`superadmin`. Поведение остаётся прежним — мультитенантность вы заметите, только
когда создадите вторую организацию.

## API

| Эндпоинт | Назначение |
| --- | --- |
| `/api/organizations` | CRUD организаций и участников для супер-админа. |
| `/api/auth/me` | Возвращает `superadmin` и список `orgs` вызывающего. |
| `X-Ravix-Org: <id>` | Заголовок, которым супер-админ действует внутри арендатора. |

## Честные ограничения

- **Фронтенд покрыт частично** — переключатель организаций и управление
  участниками выведены не на всех страницах.
- **Квоты не принуждаются.**
- **Почтовый стек общий.** У арендатора не может быть своего тюнинга Postfix,
  своего IP или своей TLS-политики.
- **Операторские данные не фильтруются для показа по арендаторам** — арендатор
  не получает свой срез очереди или DMARC-отчётов.
- **Нет флоу приглашений.** Участников добавляет супер-админ.

Если рассматриваете Ravix для реселлерского хостинга, заложите время на
самостоятельный аудит изоляции. Механизм здравый и покрыт тестом на уровне
персистентности, но ещё не проходил ту состязательную проверку, которой
заслуживает настоящий мультиклиентский продукт.
