## Модель угроз

Ravix — control plane с правами root на почтовом хосте. Отсюда следует:

- **Доступ к панели = root-доступ.** Бэкенд работает от `User=root`, потому что
  ставит пакеты, пишет в `/etc/postfix` и перезагружает сервисы. Сессия
  администратора эквивалентна root-шеллу.
- **Почтовые порты обязаны быть публичными.** 25-й порт должен принимать
  соединения откуда угодно, иначе вы не получите почту. К панели это не
  относится.
- **Порт панели публичным быть не обязан.** Эта асимметрия — самое полезное, чем
  можно воспользоваться при усилении.

## Что уже усилено

| Область | Поведение |
| --- | --- |
| **Сессии** | `HttpOnly`-cookie с `SameSite=Strict`. Из JavaScript не читается, поэтому XSS не может увести сессию; `SameSite=Strict` заменяет CSRF-токен. Флаг `Secure` добавляется, когда панель отдаётся по HTTPS. Bearer-токены продолжают работать для API-ключей и скриптов. |
| **Лимит входа** | 5 неудач на имя пользователя или 20 на IP за 5 минут → блокировка на 15 минут, ответ `429` с `Retry-After`. Проверяется до сверки пароля. Настраивается через `RAVIX_AUTH_MAX_FAILURES`, `RAVIX_AUTH_MAX_FAILURES_PER_IP`, `RAVIX_AUTH_WINDOW_SECONDS`, `RAVIX_AUTH_LOCKOUT_SECONDS`. |
| **CORS** | Same-origin разрешён всегда; прочие origin — только из списка `RAVIX_CORS_ORIGINS` (по умолчанию лишь dev-сервер Vite). Никакого wildcard. |
| **Первый администратор** | Дефолтного пароля больше нет. Если `RAVIX_ADMIN_PASSWORD` не задан, генерируется случайный пароль из 20 символов и печатается один раз при старте. |
| **Размеры выборок** | Аудит ограничен 200 (максимум 500), сообщения постранично через `offset`/`limit`, логи читают ограниченное число строк на источник, очередь ограничена `RAVIX_QUEUE_MAX_ITEMS` (500). |

## Оставшиеся слабые места

Задокументированы, а не скрыты:

| Область | Состояние | Последствие |
| --- | --- | --- |
| **Привилегии процесса** | `User=root` | RCE в панели — это root на почтовом хосте. Это архитектурное: бэкенд ставит пакеты и пишет в `/etc/postfix`. Планируемое решение — узкий привилегированный хелпер плюс `sudoers`. **Считайте доступ к панели равным root-доступу.** |
| **Раскатка конфигов** | Нет dry-run, диффа и отката | Неудачное применение может сломать доставку почты. Сначала бэкапьте `/etc/postfix`. |
| **Восстановление** | Создание бэкапов работает, восстановление не завершено | Не полагайтесь на бэкапы Ravix как на единственную копию. |
| **Пароль БД по умолчанию** | Пустой | Касается только локальной dev-базы с trust-авторизацией; `install.sh` генерирует настоящий. |

## Чеклист по усилению

Пройдите его до того, как направите публичное DNS-имя на панель.

### Сеть

- [ ] **Ограничьте порт панели.** `9162` должен быть доступен только с ваших
      IP, а не из интернета:
      ```bash
      sudo ufw delete allow 9162/tcp
      sudo ufw allow from 203.0.113.5 to any port 9162 proto tcp
      ```
      Ещё лучше — не выставлять его вовсе и ходить через VPN или SSH-туннель:
      ```bash
      ssh -L 9162:127.0.0.1:9162 you@mail.example.com
      ```
- [ ] **Держите API на loopback.** `RAVIX_HTTP_HOST=127.0.0.1` — значение по
      умолчанию; оставьте его, чтобы бэкенд был доступен только через Nginx.
- [ ] **Отдавайте панель по HTTPS.** `RAVIX_DOMAIN=panel.example.com` при
      установке выпустит сертификат. Флаг `Secure` у сессионной cookie
      выставляется только по HTTPS.
- [ ] **Держите имя хоста панели отдельно** от почтового, чтобы сертификаты и
      vhost'ы не пересекались.

### Приложение

- [ ] **CORS трогать не нужно**, если вы не разносите origin'ы. Same-origin уже
      разрешён, и это обычный вариант развёртывания. Указывать origin явно надо,
      только если фронтенд отдаётся с другого хоста:
      ```bash
      RAVIX_CORS_ORIGINS=https://panel.example.com
      ```
- [ ] **Смените пароль при первом входе** и включите TOTP-2FA в
      **Настройки → Безопасность**.
- [ ] **Отдельная учётка на человека.** Общие логины делают журнал аудита
      бесполезным.
- [ ] **Используйте минимально достаточную роль** — см.
      [Мультитенантность](multi-tenant.md).
- [ ] **Ротируйте любой API-ключ**, попадавший в чат, тикет или скриншот. Ключи
      `rvx_live_…` нельзя восстановить после создания, только заменить.
- [ ] **Периодически читайте журнал аудита.** Все изменяющие действия пишутся.

### Хост

- [ ] **Держите fail2ban включённым** (установщик делает это при
      `RAVIX_FIREWALL=1`). Он покрывает SSH, SMTP и IMAP; у входа в панель
      теперь собственный лимит.
- [ ] **Ставьте обновления безопасности** и для Ravix, и для
      Postfix/Dovecot/Rspamd.
- [ ] **Ограничьте PostgreSQL loopback'ом.** Слушать наружу ему незачем.
- [ ] **Защитите env-файл** — в `/etc/ravix/ravix.env` лежат пароль базы и
      первоначальный пароль администратора:
      ```bash
      sudo chmod 600 /etc/ravix/ravix.env
      ```

### Почта

- [ ] **Не держите открытый релей.** Сгенерированный конфиг Postfix его не
      создаёт; проверяйте после любой ручной правки:
      ```bash
      sudo postconf -n | grep -E 'mynetworks|relay_domains|smtpd_relay_restrictions'
      ```
- [ ] **Требуйте аутентификацию на submission** (порты 465/587) и TLS вместе с
      ней.
- [ ] **Используйте стойкие пароли ящиков.** Скомпрометированный ящик становится
      спам-релеем, и ваш IP оказывается в блок-листе за часы.
- [ ] **Следите за очередью и разделом RBL.** Внезапный скачок очереди обычно —
      первый признак взломанного аккаунта.

### Бэкапы

- [ ] **Делайте бэкап перед каждым применением** — `sudo ravixctl backup`.
- [ ] **Забирайте бэкапы с хоста.** Бэкап, который лежит только на защищаемой им
      машине, — не бэкап.
- [ ] **Проверьте восстановление** до того, как оно понадобится. В 0.1 сценарии
      восстановления не завершены.

## Если ящик скомпрометирован

1. Отключите ящик в панели или смените пароль, затем `sudo ravixctl apply`.
2. Вычистите вредоносную почту из очереди:
   ```bash
   sudo postqueue -p | grep -c '^[A-F0-9]'
   sudo postsuper -d ALL          # удаляет ВСЮ очередь, вместе с легитимной почтой
   ```
3. Проверьте раздел **RBL** и начните делистинг, где нужно.
4. Просмотрите журнал аудита и `/var/log/mail.log` — что ещё делал аккаунт.
5. Ротируйте API-ключи, до которых он мог дотянуться.

## Разумная конфигурация развёртывания

Для продакшен-почтовика сегодня:

- Панель доступна только через VPN или SSH-туннель.
- HTTPS с настоящим сертификатом, CORS ограничен этим origin.
- 2FA на каждом админском аккаунте, по учётке на человека.
- Бэкапы уезжают с хоста еженочно, восстановление проверено.
- Fail2ban включён, обновления безопасности автоматические.
- Алерты на глубину очереди и попадание в RBL.

Относитесь к панели как к root-шеллу, потому что это он и есть.
