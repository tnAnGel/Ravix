## The shape of the system

```text
                    ┌──────────────────────────────────────────┐
   Browser ────────▶│  Nginx  :9162                            │
                    │    /       → /var/www/ravix  (Vite dist) │
                    │    /api/   → 127.0.0.1:8080              │
                    └───────────────────┬──────────────────────┘
                                        │
                             ┌──────────▼───────────┐
                             │  Quarkus backend     │
                             │  sh.ravix.*          │
                             └──┬────────────────┬──┘
                                │                │
                  ┌─────────────▼──┐    ┌────────▼──────────────────────┐
                  │  PostgreSQL    │    │  The Linux host               │
                  │  schema:ravix  │    │  systemd · apt · postmap      │
                  │  Flyway-owned  │    │  /etc/postfix · /etc/dovecot  │
                  └────────────────┘    │  DNS · certbot · log files    │
                                        └───────────────────────────────┘
```

Ravix is **not** a mail server. It is a control plane that owns configuration
and observability for one that runs on the same host.

## Backend package layout

All backend code lives under `sh.ravix`:

| Package | Responsibility |
| --- | --- |
| `auth` | Authentication, sessions, TOTP 2FA, BCrypt hashing, role checks, audit filter, tenant context. |
| `entity` | Panache entities — the persistent model. |
| `dto` | Response shapes that are not entities. |
| `rest` | JAX-RS resources; one per domain concept, all mounted under `/api`. |
| `platform` | Everything that talks to the world: host provisioning, DNS lookups, DKIM keys, certificates, queue, campaigns, DMARC/FBL/RBL scanners, Cloudflare. |
| `util` | Small shared helpers (ID generation). |

The interesting complexity is concentrated in `platform`. `ProvisioningService`
is the largest single class in the codebase for a reason: it renders the whole
mail-stack configuration from database state.

## Request lifecycle

1. Nginx terminates TLS and proxies `/api/` to `127.0.0.1:8080`.
2. `AuthFilter` resolves the caller — the `ravix_session` cookie first, then an
   `Authorization: Bearer` header — to an `AdminUser` through `AuthService`,
   rejecting unauthenticated requests
   to anything outside the small public path allowlist (`/api/auth/login`,
   `/api/auth/status`, tracking pixels, `.well-known`).
3. `OrgFilterInterceptor` applies tenant scoping to resources annotated
   `@OrgFiltered`, using the organization on the resolved user — see
   [Multi-tenancy](multi-tenant.md).
4. `AuditFilter` records mutating requests into `audit_log`.
5. The resource runs, usually reading Panache entities and sometimes calling a
   `platform` service that shells out to the host.

## Sessions and API keys

Two credentials reach the same API:

- **Session tokens** — issued by `/api/auth/login`, stored in the `auth_session`
  table, and returned to the browser as an `HttpOnly`, `SameSite=Strict` cookie.
  The token is also in the response body for non-browser clients. Optionally
  gated by TOTP 2FA, and throttled by `LoginRateLimiter`.
- **API keys** — `rvx_live_<random>`, generated by `ApiKeyService`. Only a BCrypt
  hash and the last four characters are stored, so a key is shown exactly once
  at creation. Used for the [transactional send API](api.md).

## State ownership

This is the rule that explains most of the design:

> **PostgreSQL is the source of truth. The mail stack's config files are a
> rendered artifact.**

Domains, mailboxes, aliases, filters and signatures live in the database. When
you hit **Apply**, `ProvisioningService` renders them into Postfix maps, a
Dovecot user file, OpenDKIM key tables and Rspamd overrides, runs `postmap`, and
reloads the services. Editing `/etc/postfix/ravix/*` by hand is pointless — the
next apply overwrites it.

Ravix writes into dedicated subdirectories (`/etc/postfix/ravix/`,
`/etc/rspamd/local.d/`, `/etc/dovecot/ravix-users`) rather than replacing the
distribution's main config, so your own hand-written settings outside those
paths survive.

## Why the backend runs as root

Ravix installs packages with `apt`, writes into `/etc/postfix` and
`/etc/dovecot`, runs `postmap`, manages `systemd` units and reads
root-only logs. The 0.1 systemd unit therefore uses `User=root`.

This is the largest known weakness in the current design: any remote code
execution in the panel is immediately root on the mail host. The intended fix is
a narrow privileged helper with a `sudoers` profile, so the backend itself can
drop to the `ravix` user. Until then, treat panel access as root access and
restrict the panel port accordingly — see [Security](security.md).

## Background work

| Service | What it does |
| --- | --- |
| `DomainChecker` | Live MX / SPF / DKIM / DMARC / PTR lookups per domain. |
| `DmarcScanner` | Ingests aggregate reports dropped into the DMARC inbox. |
| `FblScanner` | Ingests ARF complaints and maintains the suppression list. |
| `RblScanner` | Checks sending IPs against DNSBLs. |
| `ReputationService` | Rolling 30-day sending reputation score. |
| `CampaignSender` | Throttled campaign delivery with warm-up caps. |
| `QueueService` | Reads and manipulates the Postfix queue. |
| `TaskService` | Tracks long-running background jobs surfaced in the UI. |

DNS lookups use the JDK's built-in provider
(`com.sun.jndi.dns.DnsContextFactory`), which is why
`quarkus.naming.enable-jndi=true` is set — Quarkus disables JNDI by default and
every DNS check would silently return empty without it.

## Frontend

A conventional Vite SPA. Notable points:

- **i18n.** Russian is the default language, English is complete; the choice is
  kept in `localStorage`. `src/i18n/ru.ts` and `src/i18n/en.ts` must stay in
  sync — a test fails on key drift.
- **Auth.** The session is an `HttpOnly` cookie the browser attaches on its own,
  so no script — ours or an injected one — can read it. `localStorage` keeps only
  a boolean "signed in" hint used to pick the initial route; the server remains
  the authority, and a stale hint just means the first call 401s to `/login`.
- **Webmail.** `WebmailPage.tsx` renders message bodies through DOMPurify. Mail
  currently lives in PostgreSQL rather than being browsed over IMAP.

## Testing

| Suite | Command | Covers |
| --- | --- | --- |
| Backend units | `cd backend && mvn test` | MIME parsing, mail composition, certificates, provisioning rendering, ID generation. |
| Backend integration | `cd backend && mvn verify` | Auth flow, authorization, tenant filtering — against a real PostgreSQL started via Testcontainers (Docker required). |
| Frontend | `npm test` | Utilities, i18n key parity, component regressions. |

CI runs all three on every push and pull request.
