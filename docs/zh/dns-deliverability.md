# DNS 与送达率

[← 返回目录](README.md) · [English](../en/dns-deliverability.md) · [Русский](../ru/dns-deliverability.md)

---

让邮件*送达*，比让邮件*发出*要难得多。本页按重要性顺序介绍 Ravix 检查的各项记录。

## Ravix 执行的检查

**域名 → 你的域名 → 重新检查** 会执行实时 DNS 查询，并按记录显示通过 / 警告 /
失败。这由 `DomainChecker` 完成；命令行下 `sudo ravixctl recheck` 会对所有域名
执行同样的检查。

| 检查项 | 验证内容 |
| --- | --- |
| **MX** | 域名的 MX 指向你的邮件主机。 |
| **SPF** | 存在 `v=spf1` 记录，并授权了你的发信 IP。 |
| **DKIM** | 选择器的公钥已发布，且与 Ravix 持有的私钥匹配。 |
| **DMARC** | 存在 `_dmarc` 记录且语法正确。 |
| **PTR** | 发信 IP 有反向解析，且能正向解析回同一 IP。 |

## 你需要的记录

### 1. MX — 接收邮件

```dns
example.com.        3600  IN  MX   10 mail.example.com.
mail.example.com.   3600  IN  A    203.0.113.10
```

MX 的目标必须是带 A 记录的主机名，绝不能是 IP，也不能是 CNAME。

### 2. PTR — 你自己设不了的那一条

```dns
10.113.0.203.in-addr.arpa.  IN  PTR  mail.example.com.
```

反向解析由 IP 的所有者设置 —— 也就是你的主机服务商，通过其控制台或工单。它必须与
邮件服务器在 `HELO` 中声明的主机名一致，且该主机名要能正向解析回同一 IP。

**没有 PTR 的 IP 发出的邮件，会被大多数大型服务商直接拒收。** 这是全新邮件服务器
无法投递到任何地方的最常见原因。请优先解决它。

### 3. SPF — 谁可以代表你发信

```dns
example.com.  3600  IN  TXT  "v=spf1 mx ~all"
```

`mx` 授权你 MX 记录所指向的主机。其他发信方需显式添加：

```dns
"v=spf1 mx include:_spf.google.com ip4:203.0.113.10 ~all"
```

容易踩的坑：

- **每个域名只能有一条 SPF 记录。** 两条 `v=spf1` TXT 记录是永久性错误，
  而不会被合并。
- **10 次查询上限。** 每个 `include:`、`a`、`mx` 和 `redirect` 都消耗一次 DNS
  查询；超过十次会导致 SPF 在所有地方失败。
- `~all`（softfail）是稳妥的默认值。只有在确认所有合法发信方都已列出后，
  才改用 `-all`。

### 4. DKIM — 签名

在 **域名 → DKIM** 中生成密钥。Ravix 会在 `/etc/opendkim` 下创建私钥，配置
OpenDKIM 用它签名，并显示需要发布的 DNS 记录：

```dns
ravix._domainkey.example.com.  3600  IN  TXT  "v=DKIM1; k=rsa; p=MIIBIjANBg..."
```

请在**应用配置之前**发布它，并留出 DNS 传播时间。用缺失的密钥去验证签名，
比完全不签名更糟。

轮换密钥的做法：生成新选择器、发布、等待 TTL 过期，然后切换签名。

### 5. DMARC — 策略与报告

从监控模式开始：

```dns
_dmarc.example.com.  3600  IN  TXT  "v=DMARC1; p=none; rua=mailto:dmarc@example.com; pct=100"
```

只有在报告干净之后才逐步收紧：

| 策略 | 含义 | 何时使用 |
| --- | --- | --- |
| `p=none` | 仅监控，不采取动作 | 第 1–4 周 — 收集数据。 |
| `p=quarantine` | 将失败邮件投入垃圾箱 | 当 SPF 与 DKIM 稳定通过后。 |
| `p=reject` | 拒收失败邮件 | 稳定状态，在 `quarantine` 不再产生合法失败之后。 |

在读懂报告之前就切到 `p=reject`，会悄无声息地掐断你已经遗忘的发信方 ——
邮件列表、开票系统、你的 CRM。

## DMARC 报告摄取

把 `rua=` 指向你掌控的邮箱，然后用以下两种方式之一把聚合报告交给 Ravix：

1. **上传** — **DMARC → 上传报告**，支持 `.xml`、`.gz` 和 `.zip`。
2. **投放** — 将文件复制到 `/var/lib/ravix/dmarc/inbox`；`DmarcScanner` 会自动摄取。

之后 DMARC 页面会按来源拆分邮件量，显示谁在以你的域名发信以及其认证情况。
通过认证的陌生来源通常是转发方；未通过的陌生来源要么是伪造，要么是你自己忘了的
系统。

## 传输安全

**TLS 安全**页面负责认证之上的那一层。

| 机制 | 记录 | 效果 |
| --- | --- | --- |
| **MTA-STS** | `_mta-sts` TXT + 通过 HTTPS 提供的策略 | 要求发信方使用 TLS 并拒绝降级。 |
| **TLS-RPT** | `_smtp._tls` TXT | 发信方向你报告 TLS 失败情况。 |
| **DANE / TLSA** | `_25._tcp` TLSA | 固定你的证书 — 要求域区启用 DNSSEC。 |

DANE 仅在注册商处启用 DNSSEC 后才生效；面板会显示 DS 记录状态，并在根区反映出来
之后将该卡片变为绿色。

## RBL / 黑名单监控

**RBL** 页面对照 DNSBL（Spamhaus、SpamCop、SORBS 等）检查你的发信 IP 并记录历史，
让你从面板而不是从客户那里得知被列入黑名单。

如果被列入：请先解决根因 —— 通常是邮箱被入侵、开放中继或劣质地址列表 —— 然后再通过
黑名单自身的解封表单申请移除。不解决根因就申请解封，只会被重新列入，而且惩罚期
往往更长。

## 信誉与预热

**信誉**页面基于退信、投诉和发信量，计算滚动 30 天的发信评分。

新 IP 没有任何信誉，从它上面突然发出大量邮件，看起来与垃圾邮件群发一模一样。
Ravix 支持逐步爬坡的每日上限 —— **信誉 → 预热**。一个保守的爬坡方案：

| 天数 | 每日邮件数 |
| --- | ---: |
| 1–3 | 50 |
| 4–7 | 200 |
| 8–14 | 1 000 |
| 15–21 | 5 000 |
| 22–30 | 20 000 |

优先向*活跃*收件人爬坡。向从不打开邮件的地址发信，只会让接收方学到完全错误的信号。

## FBL / 投诉处理

反馈循环（Feedback Loop）让服务商在收件人点击「垃圾邮件」时通知你。Ravix 会摄取
投放到 `/var/lib/ravix/fbl/inbox` 的 ARF 投诉，并把地址加入抑制列表，使营销活动
自动跳过它。

请到你实际发信的那些服务商处注册反馈循环 —— 大多数大型邮箱服务商都提供 ——
并将其指向该目录。

## 收件箱送达测试

**送达率 → 收件箱测试** 会向一组测试地址发送种子邮件，并报告每封邮件落在何处。
在修改 DNS 或完成一个预热阶段之后使用它，确认你进的是收件箱而不是垃圾箱。

## 实用检查清单

- [ ] PTR 已设置，与邮件主机名一致，且能正向解析回同一 IP。
- [ ] MX 指向带 A 记录的主机名。
- [ ] 只有一条 SPF 记录，查询次数少于十次，使用 `~all`。
- [ ] DKIM 已发布且验证通过。
- [ ] DMARC 处于 `p=none` 并带 `rua=`，报告正在被摄取。
- [ ] TLS 证书与 MX 主机名匹配。
- [ ] 未被任何主流 RBL 列入。
- [ ] 若 IP 是新的，已配置预热。
- [ ] 已确认出站 25 端口开放。
